# Conformance: C4

Release 0.24.0 (milestone 2, `docs/diagrams/notes/milestone-2.md`). Support is claimed by level (decision D3): **render**
and **edit** on the subset below, its six view kinds each checking what it may show, and **read** from a Structurizr JSON
workspace. Maps draw exactly as before: `umlimator.py import` still turns Structurizr DSL, C4-PlantUML and Mermaid's C4
diagrams into maps, and nothing converts a map to typed C4 (S12).

A view of a version-2 model (`"schemaVersion": 2`) whose `diagram` is `c4.landscape`, `c4.context`, `c4.container`,
`c4.component`, `c4.dynamic` or `c4.deployment` is a C4 view. It is drawn by `lib/umlimator-all.js` (`umlimator/all`),
which the CLI's page inlines; `lib/umlimator.js`, what a map host loads, draws it as plain cards with a warning. The
vocabulary is `docs/diagrams/model.md` §2, row 23; the example is
[`examples/bookshop-c4.json`](../../examples/bookshop-c4.json), five views, whose context view is the Bookshop atlas's
root.

## The subset

C4 is notation-independent (c4model.com); the shapes are the map's card shapes (S11), and the text over them C4's three
lines.

| Concept | In the model | Drawn as |
|---|---|---|
| Person, software system, container, component | `c4.Person`, `c4.SoftwareSystem`, `c4.Container` (`parent` a system), `c4.Component` (`parent` a container); props `description`, `technology`, `external`, `shape` | the map shape `props.shape` names (`person` for a person, `box` for the rest by default), sized by its text: the name, `[Container: technology]`, the description to four lines of 220 px; external grey |
| Deployment node | `c4.DeploymentNode` (`parent` a node or none) | holding something shown, a solid box titled name over `[Deployment Node: technology]`; else the map's node shape with C4's three lines |
| Container instance | `c4.ContainerInstance` (`parent` a node); `props.container` (a declared reference: deleting the container deletes its instances) | drawn as its container |
| Relationship | `c4.Relationship`; `label` its description, `props.technology` | a solid line with an open arrow, `description [technology]` on one line, cut at 280 px |
| Implied relationship | derived when drawn, never stored: a relationship whose end a view does not show, drawn between the nearest shown owners, one a pair, none where a relationship joins them | a dashed line with an open arrow; selected and named, never edited |
| Boundary | the view's `subject`, when `nodeIds` lists it | a dashed box titled `name [Software System]` or `[Container]`, holding what it owns that the view shows |
| Dynamic view's steps | the view's `edges`: relationship ids, each once, in time order | each step `k · description [technology]`, numbered among the steps drawn |
| Comment | `uml.Comment`, `uml.CommentLink` | a note, a dashed line |

What each view may show (`c4-level`): a landscape or context view people and software systems; a container view
containers too (its subject's and other systems'); a component view the components of its subject; a dynamic view what its subject's level
draws; a deployment view deployment nodes and container instances. An element is not listed with its owner unless that
owner is the view's subject.

Rules (`src/c4/c4.js`, `src/c4/views.js`): errors `c4-level`, `c4-subject`, `c4-owner`, `c4-instance`, `c4-relationship`,
`c4-steps` (a step that is no relationship, or one listed twice); warnings `c4-zoom`, `c4-description`, `c4-technology`,
`c4-label`, `c4-title`, `c4-steps` (a step whose end the view does not show, not drawn; a view with no step),
`c4-box-line` (a deployment view's relationship with an end in or on a node drawn as a box, not drawn).

**Departures:** the shapes are the map's; an external element is grey, as c4model.com draws it, not dashed (dashed marks a
boundary and an implied line). Deployment nodes' descriptions and technologies are not asked for.

## Left out

`notes/milestone-2.md` §13: the code diagram (the atlas reaches the class view from a component instead); software
system instances and infrastructure nodes; groups; environments as data (a deployment view's title names it); a step
repeated or reworded in a dynamic view; parallel steps; relationships between instances derived from their containers';
filtered and custom views; a Structurizr JSON or DSL writer; conversion from a map. And copy and paste, per-type `diff()`
writers, deleting a view.

The Structurizr JSON reader (`readStructurizr`) reports what it does not read: implied relationships (the type works them
out), groups, perspectives, properties, urls, documentation, themes, positions, custom elements, software system
instances, infrastructure nodes, filtered, custom and image views, and style fields other than shape.

Layout limits, measured on `examples/bookshop-c4.json` and `tests/c4-stress.json`:

- Port repair and rerouting off (`repair: false`, `reroute: false`, §11); `gap` 48, `rgap` 64.
- The example's crossings, as Node's `check()` counts them: the container view 3, the component view 2 (and laid out
  down one label on a line), the dynamic view 2 right (4 and 2 labels on lines down), the deployment view 1 each way;
  pinned in `tests/c4.test.mjs` and `tests/c4-views.test.mjs`. Chrome measures text wider and counts 14 over the five
  views (CI's example loop pins it).
- `tests/m2-fixtures.test.mjs` pins the stress file. Its six edge-case views (every shape, an implied line and one hidden
  by a direct one, another container's component, deployment nodes five deep with instances, twelve steps, a 300-character
  description) are clean but for one crossing laid out down in the container view. Its generated `all` container view
  (50 elements, 70 relationships) crosses 94 times right and 98 down; `check()` finds 132 other problems right (79 pairs
  of lines sharing a line, 53 labels on lines) and 228 down (119 shared, 108 labels on lines, one boundary's header
  crossed); and the router finds no way round some cards, so lines run through them (237 right, 202 down, counted by
  line and card; every end is on its card and no label is over a card). A crowded container
  view is C4's weakest layout with repair off.
- Deleting a view's subject leaves `c4-subject` (and `c4-level` for its components) on that view: the type's
  `remove` hook does not yet take or re-point the view (`risks.md` M15).
- A description over four lines is cut with an ellipsis; its whole text is in the element's accessible name,
  `describe()` and the PDF.

## Writers: what each shows of a C4 view

Measured on `examples/bookshop-c4.json` (0.24.0); the PDF's text read back by `tests/cli.py`.

| | SVG: `handle.toSVG()`, `umlimator.py stills` | PNG: `handle.toPNG()`, `umlimator.py stills` | PDF: `umlimator.py pdf` |
|---|---|---|---|
| Elements in their shapes with three lines, boundaries, deployment boxes, relationships, implied lines, step numbers | Yes | Yes | Yes, in vectors, each view on a page of its own |
| The key of element types, shapes, the relationship and the implied line | No: the key is a piece of the page | No | Yes, under the picture |
| Text | Text, in the page's font family; not embedded unless `fontCSS` is given | Pixels | Selectable text |
| Accessible names | Each node's `aria-label` kept; the lines' `<title>` removed | None | None |
| Tables | None | None | "Elements": each element's type, technology and description, an external one marked external, an instance's container. "Lines": each relationship's description and technology (the type's `text`), a step's number |

## Accessibility

Every piece has a name: "Container Shop API, Python, FastAPI: Catalogue, basket, checkout and accounts as a JSON API";
"Software system Bookshop, a boundary holding 5 containers"; "Step 3: Relationship from Shop API to Payment provider: …";
an implied line says what it stands for and where to edit it. Text reads at 4.5:1, lines and outlines at 3:1 in both
themes, on the stage and on each element's fill (`tests/c4.html`, `tests/c4-views.html`, `tests/m2.html`). Every gesture
has a key: `D` makes a system's container view or a container's component view, `T` changes an element's type (or an
instance's container), Alt + arrows reorder a dynamic view's steps (`docs/editing.md`).

## Performance (P1)

`tests/m2-fixtures.test.mjs` on `tests/c4-stress.json`'s `all` view (50 elements, 70 relationships), CPU time, best of
seven after a warm-up, on an Apple laptop under other agents' load (14 Nov 2026): a full layout and its SVG 109 to 229 ms;
an element's description (its node grows, laid out again) 117 to 237 ms; a container's technology, which moves nothing,
109 to 231 ms (two runs).
`tests/c4.test.mjs` measured 132 to 201 ms and 135 to 191 ms for the first two on a lighter load, and the technology at 46
to 49 ms where it repaints only. Over the 100 ms target; under CI's 1 s ceiling, which the tests hold and print.
